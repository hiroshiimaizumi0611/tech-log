# HTTP QUERYメソッド解説記事 デザイン

## 目的

2026年6月にRFC 10008として公開されたHTTP `QUERY`メソッドを、REST APIの開発経験があるWebエンジニア向けに解説する。GETとPOSTだけでは表現しにくかった「複雑だが状態を変更しない検索」という課題から入り、QUERYの役割、仕様上の特徴、試し方、採用判断までを一続きで理解できる記事にする。

記事を読んだ人が、次の状態になることを目標とする。

- QUERYが正式なHTTPメソッドであると説明できる
- GET、QUERY、POSTを安全性、冪等性、ボディ、キャッシュの観点で比較できる
- HTTPの生リクエストと`curl`でQUERYリクエストを書ける
- 対応状況を確認せずに本番採用しない理由を理解できる

## 読者と記事の立場

想定読者は、REST APIを作った経験があり、複雑な検索条件をGETとPOSTのどちらで受け取るべきか迷ったことがあるWebエンジニアとする。HTTP仕様を初めて学ぶ読者向けの用語解説には広げず、必要な用語は本文内で短く補足する。

記事はQUERYの採用を無条件に推奨しない。RFCで定義された意味を説明したうえで、クライアント、サーバー、フレームワーク、プロキシ、CDN、WAFなどの対応状況を確認しながら試す、という結論にする。特定製品の対応可否は、公式資料で確認できない限り断定しない。

## 本文構成

### 1. HTTP QUERYメソッドが正式公開された

RFC 10008が2026年6月にStandards Trackで公開されたことを示す。QUERYは、リクエスト内容をボディに含めながら、安全かつ冪等にサーバー側の問い合わせ処理を実行するためのメソッドであると説明する。

冒頭で「URLの`?q=...`部分を指すqueryとは別である」「GETにボディを付けただけのものではない」という誤解を解く。

### 2. GETとPOSTだけでは何が困るのか

GETでは、長い条件や構造化された条件をURIへ載せると、長さ、エンコード、ログへの露出、リソース識別の扱いが問題になりやすいことを説明する。

POSTならボディを利用できるが、そのリクエストが読み取り専用で安全・冪等な問い合わせであることを、HTTPメソッドの意味だけでは表現できない。QUERYはこの間を埋めるために定義された、とつなぐ。

### 3. GET・QUERY・POSTの違い

比較表には、少なくとも次の列を含める。

- 安全か
- 冪等か
- リクエストボディの意味
- キャッシュ
- 主な用途

RFC 10008の比較表を根拠にしつつ、転載ではなく日本語で要約する。POSTは常に危険・非冪等という意味ではなく、「メソッドとして安全性や冪等性が保証されない」と表現する。

### 4. QUERYリクエストを書いてみる

複雑な商品検索をJSONで送る例を使う。次の2種類を掲載する。

1. HTTPの生リクエスト
2. `curl -X QUERY`による送信例

例は架空の`https://api.example.com/products/search`へ送る。`Content-Type: application/json`と`Accept: application/json`を含め、価格帯、タグ、在庫有無などをJSONで表す。実在サービスへそのまま送れる例とは説明しない。

### 5. QUERYで押さえる仕様

入門記事として必要な次の要点に絞る。

- リクエスト内容がある場合、`Content-Type`が必要
- 非対応のメディアタイプには`415 Unsupported Media Type`を利用できる
- 内容を理解できても処理できない場合は`422 Unprocessable Content`を利用できる
- サーバーは`Accept-Query`で対応する問い合わせ形式を示せる
- `OPTIONS`の`Allow`でQUERY対応を発見できる
- 条件付きリクエスト、キャッシュ、`Location`、`Content-Location`を利用できる

細かなリダイレクトやRange Requestの規則は本文の中心にせず、必要に応じてRFCへのリンクで補う。

### 6. すぐ本番採用できるとは限らない

採用前の確認項目として、次を挙げる。

- HTTPクライアントが任意のメソッドを送信できるか
- サーバーやルーターがQUERYを受け付けられるか
- リバースプロキシ、CDN、WAFが拒否・変換しないか
- キャッシュキーと再利用条件を設計できるか
- ログ、監視、アクセス制御がQUERYを正しく扱えるか
- クロスオリジンのブラウザ利用ではCORSプリフライトが発生することを考慮したか

「安全」は認証・認可が不要という意味ではない。問い合わせ内容に秘密情報を入れてよいという意味でもない、と明記する。

### 7. QUERYを選ぶ判断基準

次の判断に着地させる。

- 単純で短い読み取り条件: GETを優先
- 複雑で長い、構造化された読み取り専用検索: QUERYを候補にする
- 状態変更を伴う処理: POSTなど、処理の意味に合うメソッドを使う
- 経路上の対応が確認できない: 既存のGETまたはPOSTを維持する

最後に、小さな検証環境でクライアントからオリジンサーバーまでの経路を通して確認してから採用するよう促す。
