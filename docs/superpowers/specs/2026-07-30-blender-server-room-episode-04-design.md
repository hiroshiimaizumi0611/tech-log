# Blender 3Dサーバールーム連載 第4回 設計書

作成日: 2026-07-30
状態: ユーザー承認済み
対象: 第4回「React Three Fiberで3Dサーバールームを表示し、アラームで色を変える」

## 1. 第4回では3Dモデルと監視状態をReactでつなぐ

第3回で書き出したGLBをReactへ読み込み、ブラウザ上で回転・ズームできるようにする。さらに、3D上でサーバーを選択し、右側の詳細パネルからアラームを発生・解除できるところまで実装する。

アラームを発生させたサーバーは緑から赤へ変わり、「正常に戻す」を押すと緑へ戻る。監視データはローカルの仮データを使い、AWSや外部APIとは接続しない。

この設計は、連載全体の設計書に記載した第4回の範囲を拡張する。当初はGLBの表示とカメラ操作までを予定していたが、ユーザーとの検討により、クリック選択、詳細パネル、仮のアラーム連動を第4回へ含めることにした。

第3回の記事では「正常なサーバーは灰色」と予告していたが、第4回では正常を緑、障害を赤とする。第4回の記事を公開するときに、第3回の該当箇所も実装結果に合わせて緑へ修正する。

## 2. 今回の完成状態

PCブラウザで次の一連の操作ができる状態を完成とする。

1. 3Dサーバールームを表示する。
2. マウスまたはトラックパッドで視点を回転・ズームする。
3. 3D上のサーバーをクリックする。
4. 右側のパネルでサーバー名、役割、IPアドレス、状態を確認する。
5. 「アラーム発生」を押し、選択中のサーバーを緑から赤へ変える。
6. 「正常に戻す」を押し、赤から緑へ戻す。

状態は色だけで伝えず、詳細パネルにも「正常」「障害」と表示する。

## 4. 第3回の検証環境を残したままViteを追加する

制作リポジトリの現在の作業ツリーには、第2回の`.blend`に未保存の変更がある。そこには触れず、`episode-03`タグを起点に、第4回用のブランチと別のworktreeを作る。

既存の`package.json`と`package-lock.json`には、GLBを検証するための`gltf-validator`とPythonテストが登録されている。空のディレクトリを前提にしたViteの初期化コマンドは使わず、必要な依存関係と設定ファイルを既存プロジェクトへ追加する。

スクリプトは次の役割に分ける。

| スクリプト | 役割 |
| --- | --- |
| `dev` | Viteの開発サーバーを起動する |
| `build` | TypeScriptを検査してProduction buildを作る |
| `preview` | Production buildをローカルで確認する |
| `lint` | ReactとTypeScriptのコードを検査する |
| `test:episode-03` | 既存のPythonテストを実行する |
| `test:unit` | 第4回のVitestを実行する |

`validate:episode-03`の内容は変更しない。Vite導入後も、第3回のテストとValidatorが成功することを完了条件に含める。

## 5. GLBのオブジェクト名を監視データのキーにする

第3回で保持したオブジェクト名を、そのままReact側の識別子に使う。

```text
server_01_01
server_01_02
...
server_02_08
```

クリックしたオブジェクト名が`server_`で始まる場合だけ選択対象にする。床、壁、ラックをクリックしても監視状態は変更しない。

第3回の成果物`models/episode-03-server-room.glb`は変更しない。同一内容を`public/models/server-room.glb`へ配置し、Viteから`/models/server-room.glb`として読み込む。2ファイルのSHA-256が一致することを確認する。

## 6. 小さなコンポーネントに責務を分ける

想定する構成は次のとおり。

```text
src/
├─ components/
│  ├─ dashboard/
│  │  └─ ServerDetailsPanel.tsx
│  └─ three/
│     ├─ ServerRoomCanvas.tsx
│     └─ ServerRoomModel.tsx
├─ data/
│  └─ servers.ts
├─ types/
│  └─ server.ts
├─ utils/
│  ├─ objectName.ts
│  └─ statusColor.ts
├─ App.tsx
├─ App.css
└─ main.tsx
```

### `App.tsx`

選択中のサーバーIDと、14台分の状態を管理する。状態管理にはReactの`useState`を使い、ContextやZustandは導入しない。

### `ServerRoomCanvas.tsx`

Canvas、カメラ、ライト、OrbitControlsをまとめる。モデル固有のクリック処理や状態管理は持たない。

### `ServerRoomModel.tsx`

GLBを読み込み、クリックされたサーバーIDを親へ通知する。Reactから受け取った状態に応じて、サーバーの色を更新する。

### `ServerDetailsPanel.tsx`

選択中サーバーの情報と状態を表示する。「アラーム発生」と「正常に戻す」の操作を親へ通知する。

### `servers.ts`

14台分のID、表示名、役割、IPアドレスを定義する。今回の状態はReactで管理し、静的なサーバー情報と分離する。値は次の規則で作る。

- 表示名: `Server 01-01`のように、オブジェクトIDの数字を使う。
- IPアドレス: `server_01_01`を`10.0.1.11`、`server_02_08`を`10.0.2.18`とし、末尾はサーバー番号へ10を足す。
- ラック1の役割: 01〜02は`Web`、03〜04は`Application`、05〜06は`Worker`。
- ラック2の役割: 01〜02は`Database`、03〜04は`Cache`、05〜06は`Monitoring`、07〜08は`Backup`。

## 7. 状態変更はReactから3Dモデルへ一方向に渡す

データの流れは次のとおり。

```text
3D上のサーバーをクリック
  ↓
ServerRoomModelがサーバーIDを通知
  ↓
AppがselectedServerIdを更新
  ↓
ServerDetailsPanelに対象サーバーを表示
  ↓
「アラーム発生」または「正常に戻す」
  ↓
Appが対象サーバーのstatusを更新
  ↓
ServerRoomModelがstatusに応じて色を更新
```

状態は次の2種類に限定する。

```ts
type ServerStatus = 'healthy' | 'critical';
```

- `healthy`: `#22C55E`、表示名は「正常」
- `critical`: `#EF4444`、表示名は「障害」

選択中のサーバーは、状態色を変えずにThree.jsの`MeshStandardMaterial`へ`#38BDF8`の発光を`0.45`で加える。非選択時の発光は黒、強度は`0`とする。これにより、正常・障害と選択状態を混同しない。

## 8. 共有マテリアルをサーバーごとに複製する

第3回のGLBでは、14台のサーバーが`mat_server_gray`を共有している。そのまま色を変更すると、1台のアラームで全サーバーの色が変わる。

ReactでGLBを読み込んだ後、シーンを複製し、`server_`で始まるMeshのマテリアルを個別に複製する。以後は各Meshのマテリアルだけを更新する。床、壁、ラックのマテリアルはGLB本来の色を維持する。

コンポーネントの再描画ごとにマテリアルを増やさないよう、シーンとマテリアルの複製は初回だけ行う。コンポーネントを破棄するときは、複製したマテリアルを解放する。

## 9. 読み込み失敗を白紙画面にしない

GLBの読み込み中は、3D領域に「3Dモデルを読み込んでいます」と表示する。

読み込みに失敗した場合は、次を表示する。

- 「3Dモデルを読み込めませんでした」
- 確認するパス`/models/server-room.glb`
- ファイルの配置場所を確認する案内

監視データにないオブジェクト名は安全に無視する。状態更新は選択中の1台だけに適用し、ほかのサーバーへ影響させない。

## 10. 画面はPC向けの2カラムにする

左側を約70%、右側を約30%とし、左に3D表示、右に詳細パネルを置く。

未選択時の詳細パネルには、「3D画面からサーバーを選択してください」と表示する。選択後は次を表示する。

- サーバー名
- オブジェクトID
- 役割
- IPアドレス
- 状態
- 「アラーム発生」ボタン
- 「正常に戻す」ボタン

正常時は「正常に戻す」を無効にし、障害時は「アラーム発生」を無効にする。現在と同じ状態への更新は行わない。

画面が狭い場合は上下に並べる。ただし、スマートフォン固有のジェスチャーや表示性能までは検証対象にしない。
