## HTTP QUERYメソッドが正式公開された

2026年6月、HTTPの新しいメソッドを定義する[RFC 10008](https://www.rfc-editor.org/rfc/rfc10008.html)がStandards TrackのProposed Standardとして公開されました。新しいメソッドの名前は`QUERY`です。[IANAのHTTP Method Registry](https://www.iana.org/assignments/http-methods/http-methods.xhtml)にも登録されています。

QUERYは安全かつ冪等なメソッドです。安全とは、クライアントが対象リソースの状態変更を意図しないこと、すなわちサーバーにその変更を要求も期待もしない性質を指します。サーバーによるログの記録や結果用リソースの作成まで禁じる性質ではありません。また、認証なしで使える、機密情報を含まない、あるいは実行しても一切害がない、という意味でもありません。冪等とは、同じリクエストを繰り返しても意図した効果が同じであることです。時刻やデータ更新によってレスポンスまで毎回同一になる、という意味ではありません。これらの用語は[HTTP Semantics（RFC 9110）](https://www.rfc-editor.org/rfc/rfc9110.html)でも定義されています。

名前が似ていますが、QUERYメソッドとURIのクエリコンポーネントは別物です。`?q=...`はURIの一部であり、`QUERY`はリクエスト行に書くHTTPメソッドです。

> QUERYは、読み取り専用の複雑な問い合わせをURIではなくリクエスト内容で表現するためのHTTPメソッドです。

## GETとPOSTだけでは何が困るのか

商品検索を例にします。価格帯、複数のタグ、在庫状態、並び順などを指定すると、GETのURIは長くなり、入れ子構造も表しにくくなります。一方、POSTならJSONを送れますが、POSTというメソッド自体は安全性や冪等性を保証しません。読み取り専用であることをHTTPのメソッドとして伝えたい場面では、この差がキャッシュや再試行の判断を難しくします。

だからといって、GETやPOSTが不適切になるわけではありません。短く単純な取得条件ならGETが自然です。対象リソースが定めた処理を依頼し、その処理が状態変更を含み得るならPOSTが適しています。QUERYは、その間にある「複雑だが読み取り専用の問い合わせ」を明示する選択肢です。

RFC 10008では、QUERYのリクエスト内容には対象リソースが定義した意味があるとしています。つまり、JSONの項目や検索式をHTTPが共通に決めるのではなく、APIごとに仕様を定めます。

## GET・QUERY・POSTの違い

<!-- prettier-ignore -->
| 観点 | GET | QUERY | POST |
| --- | --- | --- | --- |
| 安全 | はい | はい | メソッドとしては保証されない |
| 冪等 | はい | はい | メソッドとしては保証されない |
| リクエストボディ | 意味は定義されていない | 問い合わせ内容を入れる | 対象リソースの意味に従う |
| キャッシュ | 可能 | 可能 | 制約付きで可能 |
| 主な用途 | 短く単純な取得条件 | 複雑な読み取り専用検索 | 状態変更を含み得る処理 |

QUERYはキャッシュ可能ですが、キャッシュキーにはリクエスト内容と関連メタデータを含める必要があります。メソッドとURIだけでは、異なる検索条件を区別できません。RFC 10008が定めるこの性質をキャッシュ層まで正しく扱えるか、採用前に確認します。

## QUERYリクエストを書いてみる

たとえば、商品検索APIにJSONで条件を送るHTTPリクエストは次の形です。`Content-Type`は、リクエスト内容のメディアタイプを対象リソースへ伝えます。

```http
QUERY /products/search HTTP/1.1
Host: api.example.com
Content-Type: application/json
Accept: application/json

{
  "price": { "min": 1000, "max": 10000 },
  "tags": ["http", "api"],
  "inStock": true
}
```

[curlのオプション](https://curl.se/docs/manpage.html)を使うと、同じ内容を次のように送れます。

```bash
curl --request QUERY 'https://api.example.com/products/search' \
  --header 'Content-Type: application/json' \
  --header 'Accept: application/json' \
  --data '{
    "price": { "min": 1000, "max": 10000 },
    "tags": ["http", "api"],
    "inStock": true
  }'
```

`api.example.com`は説明用です。この例が成功するのは、クライアントから対象APIまでの経路全体がQUERYに対応し、`/products/search`がこのJSON形式を受け付ける場合だけです。

## QUERYで押さえる仕様

QUERYのリクエスト内容の形式は対象リソースが決めます。サーバーは`OPTIONS`へのレスポンスの`Allow`でQUERYを利用可能なメソッドとして通知でき、`Accept-Query`で対応する問い合わせのメディアタイプを列挙できます。クライアントはここから、たとえば`application/json`を送れるか判断できます。

`Content-Type`などのメディアタイプ情報がない場合は、4xx（たとえば`400 Bad Request`）で拒否します。宣言されたメディアタイプが実際の内容と一致しない場合も、`400 Bad Request`が候補です。宣言されたメディアタイプが対象リソースで対応していない場合は、`415 Unsupported Media Type`が適切です。メディアタイプが対応済みで内容とも一致していても、問い合わせ内容の意味によって処理できない場合は、`422 Unprocessable Content`が候補になります。どの形式とエラーを採用するかは、対象APIの契約として明記します。

RFC 10008では、QUERYのレスポンスに再利用できるURIを示す方法も定めています。Locationは同じ問い合わせを再実行できるリソースを識別し、クライアントはそのURIへGETできます。Content-Locationは返された結果に対応するリソースを識別します。両者は目的が異なるため、同じURIになるとは限りません。

QUERYではETagなどを使った条件付きリクエストも利用できます。ただし、条件を評価する対象とキャッシュキーには、URIだけでなく問い合わせの内容も関わります。既存のGET向けキャッシュ設定はそのまま流用せず、QUERYの仕様に沿って検証します。

## すぐ本番採用できるとは限らない

RFCが公開されていても、リクエストがアプリケーションまで届くとは限りません。採用前に、クライアント、ルーター、リバースプロキシ、CDN、WAF、キャッシュ、ログ、監視、認証、認可がQUERYをエンドツーエンドで正しく扱うか確認します。不明なメソッドの拒否、リクエスト内容の破棄、誤ったキャッシュ共有、ログからの検索条件欠落などを実際の経路で試します。

ブラウザから別オリジンへ送る場合も注意が必要です。[Fetch Standard](https://fetch.spec.whatwg.org/)上、QUERYはCORS-safelisted methodではないため、CORSプリフライトが必要です。サーバー側はプリフライトへの応答でQUERYを許可し、必要なヘッダーも許可しなければなりません。

なお、`Allow`や`Accept-Query`による通知は重要ですが、それだけで経路上のすべての装置が対応しているとは証明できません。検証環境で送信、転送、認可、応答、キャッシュ、観測までを通して確認します。

## QUERYを選ぶ判断基準

条件が短くURIで明快に表せるなら、GETを第一候補にします。状態変更を含み得る処理や、対象リソースの意味に従う汎用的な処理ならPOSTを選べます。読み取り専用の複雑な問い合わせをリクエスト内容で表現し、安全・冪等という意味をプロトコル上でも保ちたい場合にQUERYを検討します。

RFCを読んだだけでは採用判断は終わりません。利用する経路の実装と運用も確認します。

- 問い合わせが読み取り専用で、安全かつ冪等である
- GETのURIでは条件が長い、または構造を明快に表しにくい
- `Content-Type`と問い合わせ形式をAPI契約に定めている
- `OPTIONS`、`Allow`、`Accept-Query`による発見方法を設計している
- キャッシュキーがリクエスト内容と関連メタデータを区別する
- 条件付きリクエスト、`Location`、`Content-Location`の扱いを決めている
- CORSプリフライトを含め、エンドツーエンドで動作確認している
- GETやPOSTのほうが単純で相互運用しやすくないか再確認している
